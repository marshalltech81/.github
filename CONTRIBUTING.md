# Contributing

Thank you for your interest in contributing.

This document explains how to participate in this project and how to make contributions easier to review and merge.

## Before you start

Please read and follow:

- `CODE_OF_CONDUCT.md`
- `SECURITY.md`
- `SUPPORT.md`

Use the appropriate GitHub issue template when opening bugs or feature requests.

Do not open public issues for security vulnerabilities. Follow the reporting instructions in `SECURITY.md`.

## Types of contributions

Contributions are welcome in areas such as:

- bug fixes
- documentation improvements
- test improvements
- small focused features
- developer experience improvements
- issue triage and reproduction help

## Before opening a pull request

Before starting major work:

- check existing issues and pull requests for duplicates
- open an issue first for large features, breaking changes, or broad refactors
- keep scope narrow and focused on one concern

## Development expectations

When contributing:

- prefer small, reviewable changes
- avoid unrelated cleanup in the same pull request
- follow existing patterns in the repository
- prefer the simplest solution that fully solves the problem
- update documentation when behavior changes
- add or update tests when appropriate

## Branches

Create your work on a topic branch and open a pull request against the default branch unless the repository says otherwise.

## Commit and pull request conventions

Use clear, descriptive pull request titles.

Unless a repository says otherwise, use Conventional Commits for pull request titles and final squash-merge commit titles:

- `feat:`
- `fix:`
- `docs:`
- `refactor:`
- `test:`
- `build:`
- `ci:`
- `chore:`

Examples:

- `fix: handle missing configuration file`
- `docs: clarify local setup steps`
- `feat: add retry support for webhook delivery`

Mark breaking changes clearly with `!` or `BREAKING CHANGE:` when applicable.

## Pull request checklist

Before opening a pull request, confirm that you have:

- kept the change focused
- updated tests if needed
- updated documentation if needed
- run relevant validation for the changed code
- described the change clearly in the pull request

## Code review

Reviews focus primarily on:

- correctness
- security
- reliability
- maintainability
- test coverage where relevant

Please respond constructively to review feedback and keep discussion focused on the change.

## Documentation contributions

Documentation should be:

- clear
- concise
- accurate
- easy to scan

Prefer:

- plain language
- short paragraphs
- numbered steps for procedures
- relative links for internal repository references

## Reporting bugs

When reporting a bug, include:

- what happened
- what you expected to happen
- steps to reproduce
- environment or version details if relevant
- logs or screenshots when helpful

Use the bug report template when available.

## Suggesting features

When suggesting a feature, describe:

- the problem to solve
- the proposed solution
- alternatives considered
- any relevant constraints or context

Use the feature request template when available.

## Security issues

Do not report security issues in public issues or pull requests.

Follow the instructions in `SECURITY.md`.

## Questions and support

For questions, help, or general discussion, use the support path described in `SUPPORT.md`.

## Maintainer discretion

Maintainers may decline contributions that:

- significantly increase scope without clear need
- do not fit the direction of the project
- weaken security, validation, or maintainability
- duplicate existing or planned work
